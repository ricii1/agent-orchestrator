## Tujuan produk dan pekerjaan utama pengguna

Pertahankan **satu PM dan freelancer sementara dalam kantor piksel**. Freelancer hadir saat mengantre/bekerja/menunggu, lalu pergi setelah selesai; hasilnya tetap di riwayat. Tidak ada staf permanen, XP, departemen, ranking, atau ekonomi game ([README](../../README.md), [ROADMAP](../ROADMAP.md), [S] web/model.ts:4–11).

[H] Pengguna utama adalah pemilik proyek lokal yang ingin memberi tujuan ke PM, memahami siapa mengerjakan apa, menjawab hambatan, lalu meninjau hasil. Alur target: **pilih konteks → beri tujuan → pantau/beri keputusan → tinjau hasil/perubahan → lanjutkan bila terputus**. Keberhasilan redesign berarti konteks dan tindakan berikutnya terbaca tanpa membuka detail teknis, sementara kontrol teknis tetap tersedia.

## Arah IA dan visual untuk Designer

1. **Konteks tetap:** workspace aktif dengan path yang dapat diakses, PM/provider, koneksi, dan akses Riwayat/Terminal. Provider change memperjelas bahwa percakapan terpisah tetap tersimpan.
2. **Area kerja utama:** percakapan PM, composer, serta permintaan keputusan. Worker log hanya-baca dengan “Kembali ke PM” yang jelas; jangan menambahkan composer worker yang menyiratkan arahan langsung.
3. **Kantor piksel:** tetap terlihat pada desktop dan mudah dibuka pada mobile. PM tetap, freelancer sementara; daftar tekstual adalah kontrol setara. Meja kosong berarti kapasitas, bukan posisi staf yang harus direkrut permanen.
4. **Riwayat/detail:** status → ringkasan hasil/hambatan → log → executionPath/branch → diff → integrasi bila tersedia. Bedakan “hasil selesai” dengan “sudah digabung”; jangan menciptakan status backend baru.
5. **Pengaturan sekunder:** kelompok sesuai A9, kuota sebagai informasi akun pendukung. Terminal adalah panel shell terpisah dengan konteksnya sendiri, bukan mode PM yang diam-diam berubah.

Pertahankan rasa hangat kantor: latar krem, aksen hijau/biru, sprite pixel dan furnitur yang sudah ada; teks UI tetap font biasa. Naikkan kontras dan hierarki: body/chat sekitar 14–16 px, label fungsional sekitar 12–14 px sebagai titik awal desain (bukan ukuran final yang menggantikan pengujian). Status memakai teks + ikon/bentuk selain warna. Batasi dekorasi yang mengurangi ruang baca; tidak memerlukan aset bitmap/ilustrasi baru. Tentukan token warna, ukuran, spacing, fokus, error dan status sebelum membuat varian layar.

Contoh copy yang perlu diselesaikan Designer: “Freelancer mulai dari commit terakhir”, “Izin ini berlaku di semua workspace”, “Pertanyaan ini masih perlu jawaban”, “Terputus — tinjau aktivitas sebelum melanjutkan”, dan “Terminal langsung ke shell; output tidak masuk ke PM”. Jangan mengklaim akses penuh tetap bersandbox.

- [ ] Petakan semua A1–A11 ke layar/komponen atau alasan penundaan; P0 diselesaikan sebelum polishing. Sediakan alur workspace pertama → tujuan PM → menunggu keputusan → hasil/diff dan terputus → review → lanjutkan.

- [ ] Sertakan state tanpa workspace, belum ada chat, loading transcript, PM/worker berjalan, antre, pertanyaan, izin provider, form invalid, failed/interrupted/cancelled, riwayat kosong, reconnect, serta quota loading/unavailable/stale/available dan terminal opening/active/hidden/ended/error.
- [ ] Annotasikan actor/workspace/provider/cakupan untuk keputusan; manual/auto/full, simpan per bagian dan efek pending. Tampilkan perbedaan source vs PNG pada pengaturan; jangan menyalin PNG sebagai state terkini.
- [ ] Hasil handoff memuat IA, komponen/token, copy final, aturan responsive/fokus, dan matriks state → data/aksi yang sudah tersedia. Tandai kebutuhan data yang belum tersedia sebagai batas, bukan janji implementasi. Tidak ada staf permanen/XP/departemen atau fitur backend baru.

### Untuk Frontend Developer, setelah desain disetujui PM

- [ ] Konteks workspace/provider terpilih selalu dapat dibaca; folder bernama sama dapat dibedakan lewat path tanpa hover saja. Panduan HEAD statis muncul sebelum delegasi pertama; detail menampilkan executionPath/branch yang tersedia tanpa klaim deteksi dirty baru.
- [ ] Pergantian workspace/provider memulihkan draft yang sesuai dalam sesi UI; chat worker tetap hanya-baca; hasil worker selesai tetap dapat dibuka dari riwayat. Reload tidak dijanjikan mempertahankan draft bila belum didukung.
- [ ] Semua pending request menyebut actor dan tugas, walau chat lain dipilih. Command/host/path dan cakupan opsi provider tidak dipotong semantik. Tidak ada approval/jawaban otomatis akibat redraw atau pemilihan opsi. Error submit mempertahankan jawaban; busy mencegah submit ganda.

Membaca pesan lama tidak dipaksa scroll ke bawah; pesan baru dapat ditemukan tanpa kehilangan posisi. Fokus keyboard tidak hilang ketika state/SSE redraw.
- [ ] Tugas gagal/terputus/dihentikan dapat ditelusuri ke hasil/log sebelum lanjutkan eksplisit; tidak auto-resume. Aksi Hentikan PM menjelaskan anak aktif. Review/merge menjelaskan konsekuensi existing, bukan menawarkan rollback otomatis yang tidak ada.
- [ ] Kuota unavailable tidak menjadi nol; stale tetap berlabel, timestamp/reset terlihat tanpa hover dan refresh dapat diakses mobile. Status penting diumumkan tanpa membaca ulang seluruh log. Reflow 320 CSS px dan zoom teks 200% tanpa kehilangan aksi; area kode/terminal boleh scroll lokal. Reduced motion dan alternatif tombol canvas tetap berfungsi.
- [ ] Validasi terarah di fixture/demo terisolasi: alur pertama, keputusan valid/invalid, provider switch, history/recovery, API error/SSE reconnect, viewport/keyboard, serta terminal/quota state tanpa provider nyata. Jalankan check/test/build yang relevan saat implementasi; review diff memastikan source orang lain tetap dipertahankan. Jangan menjalankan provider/daemon produksi demi validasi visual tanpa penugasan terpisah.

## Keputusan review dan batas validasi

Rekomendasi urutan pengerjaan: **A1–A3 → A4–A8/A11 → A9–A10**, dengan perbaikan mobile/aksesibilitas diterapkan sejak fondasi komponen. PM mereview prioritas dan pembagian ruang; setelah itu menugaskan Designer, lalu Frontend berdasarkan desain yang disetujui. Analis tidak menugaskan worker tambahan.

Hipotesis yang masih perlu diuji setelah prototipe: apakah path + panduan commit cukup mencegah salah konteks; apakah chat lebih dominan tetap menjaga identitas kantor; apakah pengguna membedakan izin/pertanyaan/terminal; apakah mereka bisa menemukan hasil freelancer yang sudah pergi dan melanjutkan tugas terputus dengan sadar. Ini agenda validasi berikutnya, bukan hasil user testing saat ini. Metrik kandidat: keberhasilan memilih workspace, menemukan hasil, memahami cakupan izin, dan menyelesaikan pemulihan; belum ada baseline atau angka target empiris.

Pemeriksaan untuk artefak ini: pembacaan source saat ini, inspeksi dua PNG, browsing empat sumber resmi, pemeriksaan struktur/link lokal dan scope perubahan dokumen. Tidak menjalankan test/build karena hanya analisis Markdown; tidak memvalidasi runtime mobile, screen reader, rasio kontras, provider nyata, terminal, kuota live, atau penyebab kegagalan tugas. Referensi eksternal adalah pembanding pola, bukan bukti aplikasi Kantor. Pekerjaan unstaged/untracked lain dipertahankan; tidak stage/commit/merge/push/deploy/restart atau mengubah `.git`/`.data`.
